chapitre 0 introduction du cours

ce que le cours est, et ce qu'il n'est pas

le cours « langage interprété » part du principe que tu sais déjà programmer. les slides d'introduction le disent explicitement : ce cours n'est pas conçu pour comprendre les bases de l'algorithmique ou de la programmation, ni pour découvrir le paradigme de l'orienté objet, ni pour étudier la syntaxe de python. python est le support, pas le sujet.

le vrai sujet, ce sont les trois objectifs annoncés :

  • découvrir les spécificités d'un langage interprété moderne et de son écosystème logiciel ;
  • maîtriser l'organisation d'un projet logiciel ;
  • préparer aux pratiques d'ingénierie logicielle et aux environnements devops.

autrement dit : on n'apprend pas à écrire une boucle, on apprend à travailler comme un ingénieur qui livre un projet python propre, installable et reproductible sur une autre machine.

1.1 l'échelle d'abstraction des langages

un processeur n'exécute qu'une seule chose : du langage machine, c'est-à-dire des instructions binaires propres à son architecture. personne n'écrit directement en binaire. tous les langages de programmation sont des couches d'abstraction empilées au-dessus du langage machine, et le cours les range du plus bas niveau (proche de la machine) au plus haut niveau (proche de l'humain) :

niveaucatégorieexemples du cours
haut niveau ↑langages interprétésjavascript, python
langages compilésc++, c
langage assembleurx86, mips
bas niveau ↓langage machinele binaire exécuté par le processeur

plus on monte, plus le code est lisible, court et indépendant de la machine ; plus on descend, plus on contrôle finement le matériel, mais plus le code est lié à un processeur précis. l'assembleur n'est qu'une écriture lisible du langage machine : il dépend donc de l'architecture (x86 pour les pc, mips pour d'autres processeurs). les langages compilés et interprétés sont tous deux de « haut niveau » par rapport à l'assembleur ; ce qui les distingue, c'est la façon dont leur code source finit par être exécuté.

1.2 la compilation

dans un langage compilé, l'exécution se fait en deux temps bien séparés. d'abord on compile, ensuite on exécute :

$ gcc hello.c -o hello     # 1. compilation : le compilateur gcc produit le binaire "hello"
$ ./hello                  # 2. exécution : on lance directement le binaire

le schéma du cours est : code source → compilateur (gcc) → code machine → exécution. le compilateur est un programme qui lit tout le code source et produit un fichier en code machine. une fois ce fichier produit, on n'a plus besoin ni du code source ni du compilateur pour lancer le programme.

d'après le cours, le compilateur fait trois choses :

  • la traduction vers le langage machine ;
  • la vérification de certaines erreurs (erreurs de syntaxe, de typage, …) avant même que le programme tourne ;
  • des optimisations adaptées à la machine cible : comme il connaît le processeur visé et voit tout le programme, il peut réorganiser le code pour qu'il aille plus vite.

1.3 l'interprétation

dans un langage interprété, il n'y a qu'une seule commande, et pas de fichier binaire produit :

$ python hello.py          # l'interpréteur lit le code source et l'exécute directement

le schéma devient : code source → interpréteur → exécution. l'interpréteur est un programme qui doit être présent sur la machine à chaque exécution : c'est lui qui lit le code source et le fait tourner. le cours retient deux caractéristiques :

  • la traduction vers le langage machine se fait en temps réel, pendant que le programme s'exécute ;
  • la vérification des erreurs se fait à l'exécution : une erreur n'est découverte que lorsque l'interpréteur arrive sur la ligne fautive.
pour comprendre. conséquence concrète du second point : un programme python peut tourner pendant dix minutes puis planter sur une faute de frappe dans un nom de variable, à la ligne 300. en c, la même faute aurait empêché la création du binaire, donc le programme n'aurait jamais démarré.

1.4 compilation contre interprétation : le tableau à connaître par cœur

c'est le tableau central du chapitre. cinq critères, à savoir restituer dans les deux sens.

piège qcm. la portabilité « élevée » de l'interprété a une condition : l'interpréteur doit être installé sur la machine. et la portabilité « faible » du compilé concerne le binaire, pas le code source : un binaire compilé pour windows x86 ne tourne pas sur linux arm, il faut recompiler.

1.5 le cas de python : compilé puis interprété

python est classé parmi les langages interprétés, mais son fonctionnement réel est hybride. le schéma du cours comporte une étape de plus que l'interprétation simple :

code source → compilateur (cpython) → code intermédiaire → interpréteur (pvm) → exécution

quand tu lances python hello.py, deux choses se passent, sans que tu les voies :

  1. compilation en code intermédiaire. le compilateur de cpython (l'implémentation de référence de python, écrite en c) traduit ton code source en code intermédiaire, qu'on appelle aussi bytecode. ce n'est pas du langage machine : c'est une suite d'instructions simples, pensées pour une machine qui n'existe pas physiquement.
  2. interprétation du code intermédiaire. la pvm (python virtual machine, la machine virtuelle python) est l'interpréteur proprement dit : elle lit les instructions du code intermédiaire une par une et les exécute sur la vraie machine.
pour comprendre. pourquoi cette étape intermédiaire ? parce que le bytecode est beaucoup plus rapide à interpréter que du texte source, et qu'il reste identique sur toutes les machines. python met ce bytecode en cache dans des fichiers .pyc, dans un dossier __pycache__/, pour les modules importés : au lancement suivant, si le source n'a pas changé, la compilation est sautée. c'est pour cela qu'un dossier __pycache__ apparaît dans tes projets.

le cours compare ensuite les trois formes que peut prendre un programme :

code sourcecode machinecode intermédiaire

lisibilité✓ oui✗ non? (question ouverte sur la slide)
portabilité✓ oui✗ non✓ oui

ce tableau résume l'intérêt du code intermédiaire : il cumule l'avantage du code source (la portabilité : le même bytecode tourne partout où une pvm existe) et celui du code machine (il est prêt pour l'exécution, la pvm n'a plus à analyser du texte). pour la lisibilité, la slide laisse un point d'interrogation : le bytecode n'est pas écrit pour être lu par un humain, mais il n'est pas non plus aussi opaque que du binaire machine, puisqu'on peut l'afficher sous forme d'instructions nommées (avec le module standard dis).

pièges qcm. (1) le code intermédiaire s'adresse à la pvm, pas au processeur. (2) dans le schéma du cours, le compilateur est associé à cpython et l'interpréteur à la pvm. (3) « python est interprété » reste la bonne réponse à la question de classement, mais « il n'y a aucune compilation en python » est faux.

1.7 le gestionnaire de paquets

le gestionnaire de paquets est l'outil qui fait le lien entre ton projet et le dépôt centralisé. d'après le cours, il sert à :

  • installer des bibliothèques tierces ;
  • gérer les versions et mettre à jour les bibliothèques ;
  • désinstaller les bibliothèques.

le gestionnaire historique de python est pip. les commandes vues en tp1 :

python --version                    # version de l'interpréteur python
pip --version                       # version de pip
pip list                            # liste des bibliothèques installées dans l'environnement
pip install pillow                  # installer une bibliothèque depuis pypi
pip install --upgrade pillow        # la mettre à jour
pip uninstall pillow                # la désinstaller
pip freeze > requirements.txt       # exporter les bibliothèques installées, avec leurs versions
pip install -r requirements.txt     # réinstaller tout ce qui est listé dans le fichier

le tp1 pose la question « d'où viennent ces bibliothèques ? » devant le résultat de pip list. la réponse : pip list affiche les bibliothèques tierces présentes dans l'environnement python courant. sur une installation neuve on y trouve au minimum pip lui-même, livré avec python ; tout le reste a été téléchargé depuis pypi par un pip install. les modules de la bibliothèque standard n'apparaissent pas dans cette liste, car ils font partie de python.

le fichier requirements.txt

dans un projet, il est essentiel de répertorier les bibliothèques tierces nécessaires et leurs versions, afin de garantir la reproductibilité de l'environnement d'exécution : quelqu'un d'autre doit pouvoir installer exactement les mêmes bibliothèques. le fichier requirements.txt, placé à la racine du projet, joue ce rôle. la commande pip freeze > requirements.txt le génère automatiquement ; chaque ligne a la forme nom==version :

matplotlib==3.11.2
pillow==12.3.0
qrcode==8.2
pour comprendre. pip freeze exporte tout ce qui est installé dans l'environnement, y compris les dépendances que tes bibliothèques ont installées à leur tour (par exemple numpy, amené par matplotlib). le symbole > est une redirection du terminal : il envoie la sortie de la commande dans un fichier au lieu de l'écran.

1.8 documentation et utilisation de bibliothèques

utiliser une bibliothèque tierce, c'est d'abord savoir lire sa documentation : c'était toute la « règle du jeu » du tp1. le cours distingue où la trouver et quelles formes elle prend.

où trouver la documentation

  • sur le dépôt centralisé (la page de la bibliothèque sur pypi — c'est le cas de qrcode dans le tp1) ;
  • sur le site dédié de la bibliothèque (pillow.readthedocs.io, matplotlib.org) ;
  • sur le dépôt github du projet ;
  • directement dans le code source.

  • le système de coordonnées de pillow a son origine en haut à gauche de l'image : x augmente vers la droite, y augmente vers le bas. la méthode crop prend une boîte (gauche, haut, droite, bas).
  • la démarche : installer la bibliothèque, l'importer, chercher dans la documentation officielle la fonction qui répond au besoin, puis consigner les dépendances.

  • interprété : traduit ligne par ligne au lancement, plus lent, erreurs à l'exécution, source portable si l'interpréteur est là, cycle rapide.
  • python : source → compilateur cpython → code intermédiaire → interpréteur pvm → exécution.
  • écosystème : 3 piliers (bibliothèques tierces, dépôts centralisés, outils) et 3 couches (code développeur, bibliothèque standard, bibliothèques tierces).
  • gestionnaire de paquets : installer, gérer les versions / mettre à jour, désinstaller.
  • documentation : 4 lieux (dépôt centralisé, site dédié, github, code source), 4 types (readme, api reference, guides/tutoriels, docstrings).

2.1 deux notions préalables : mutabilité et hashabilité

le cours caractérise chaque collection par deux propriétés. il faut les comprendre avant de lire les définitions.

mutable / immuable. un objet mutable peut être modifié après sa création (ajouter, retirer, remplacer un élément) : c'est le même objet, dont le contenu change. un objet immuable (ou immutable) ne peut plus changer une fois créé : toute « modification » fabrique en réalité un nouvel objet. les nombres, les chaînes de caractères et les tuples sont immuables ; les listes, les ensembles et les dictionnaires sont mutables.

hashable. un objet est hashable si python peut lui calculer une empreinte numérique (son hash) qui ne change jamais pendant toute sa vie. les ensembles et les dictionnaires reposent sur cette empreinte pour retrouver un élément instantanément. un objet dont le contenu peut changer ne peut pas avoir d'empreinte stable : c'est pourquoi les objets mutables ne sont pas hashables, alors que les objets immuables (int, float, str, bool…) le sont.

hash("pomme")        # fonctionne : une chaîne est immuable, donc hashable
hash((1, 2))         # fonctionne : tuple d'éléments hashables
hash([1, 2])         # typeerror: unhashable type: 'list'
hash((1, [2, 3]))    # typeerror : le tuple contient une liste, il n'est pas hashable

2.2 les listes

définition du cours. une liste (list) est une structure de données qui permet de stocker plusieurs éléments dans un ordre défini. elle peut contenir des éléments de types différents. les listes sont des structures mutables.

fruits = ["pomme", "banane", "orange"]
fruits.append("kiwi")        # ajoute à la fin      -> ['pomme', 'banane', 'orange', 'kiwi']
fruits.remove("banane")      # retire cette valeur  -> ['pomme', 'orange', 'kiwi']
fruits[0] = "fraise"         # remplace par index   -> ['fraise', 'orange', 'kiwi']

la liste est la collection par défaut : on l'utilise dès qu'on a une suite d'éléments ordonnée qui doit pouvoir évoluer. les doublons y sont autorisés, et on accède aux éléments par leur position (l'index commence à 0).

2.3 les tuples

définition du cours. un tuple (tuple) est une structure de données qui permet de stocker plusieurs éléments dans un ordre défini. contrairement à une liste, un tuple est immuable.

coordonnees = (48.86, 2.35)
coordonnees[0] = 50.0        # typeerror : un tuple ne peut pas être modifié

deux propriétés à retenir :

  • les tuples sont des structures immutables ;
  • un tuple est hashable uniquement si tous ses éléments sont eux-mêmes hashables. (1, 2) peut servir de clé de dictionnaire, (1, [2, 3]) non.

l'usage mis en avant par le cours est de retourner plusieurs valeurs depuis une fonction. écrire return a + b, a * b crée en réalité un tuple :

def calculer(a, b):
    return a + b, a * b

resultat = calculer(3, 4)
print(resultat)              # (7, 12)

somme, produit = calculer(3, 4)   # on peut décomposer directement le tuple
pour comprendre. ce sont les virgules qui font le tuple, pas les parenthèses. un tuple à un seul élément s'écrit donc (5,) avec une virgule ; (5) est juste l'entier 5.

2.4 les ensembles

définition du cours. un ensemble (set) est une structure de données qui permet de stocker une collection d'éléments uniques et non ordonnés.

nombres = {1, 2, 3}
nombres.add(4)               # {1, 2, 3, 4}
nombres.remove(2)            # {1, 3, 4}
  • les ensembles sont des structures mutables ;
  • les ensembles n'acceptent que des éléments hashables (on ne peut pas mettre une liste dans un ensemble).

« non ordonné » signifie qu'il n'y a ni position ni index : nombres[0] est une erreur, et l'ordre d'affichage n'est pas garanti. « unique » signifie qu'ajouter un élément déjà présent ne change rien.

premier usage : supprimer les doublons. convertir une liste en ensemble élimine automatiquement les répétitions :

nombres = [1, 2, 2, 3, 4, 4, 5]
nombres_uniques = set(nombres)
print(nombres_uniques)       # {1, 2, 3, 4, 5}

second usage : les opérations mathématiques sur les ensembles.

a = {1, 2, 3}
b = {3, 4, 5}
print(a | b)    # union        : {1, 2, 3, 4, 5}  (dans a ou dans b)
print(a & b)    # intersection : {3}              (dans a et dans b)
print(a - b)    # différence   : {1, 2}           (dans a mais pas dans b)
pièges qcm. (1) {} crée un dictionnaire vide ; l'ensemble vide s'écrit set(). (2) a - b n'est pas symétrique : b - a vaut {4, 5}. (3) un ensemble est mutable, donc lui-même non hashable : on ne peut pas mettre un ensemble dans un ensemble.

2.5 les dictionnaires

définition du cours. un dictionnaire (dict) est une structure de données qui permet de stocker des informations sous forme de paires clé–valeur. chaque clé est unique et permet d'accéder rapidement à la valeur qui lui est associée.

personne = {
    "nom": "alice",
    "age": 25,
    "ville": "paris"
}
print(personne["nom"])       # alice
personne["age"] = 26         # modifie une valeur existante
personne["email"] = "a@b.fr" # ajoute une nouvelle paire
  • les dictionnaires sont des structures mutables ;
  • les dictionnaires n'acceptent que des clés hashables (une chaîne, un nombre, un tuple d'éléments hashables — jamais une liste) ;
  • les valeurs peuvent être de n'importe quel type, y compris une liste ou un autre dictionnaire.

accéder à une clé absente avec personne["tel"] lève une erreur keyerror ; la méthode get (vue plus bas dans les idiomes) permet de l'éviter. les méthodes .keys(), .values() et .items() donnent respectivement les clés, les valeurs et les paires.

2.7 les compréhensions

définition du cours. une compréhension construit une collection à partir d'une autre, en une seule expression. c'est « la marque de fabrique du style python ». elle remplace le processus classique : créer une liste vide → boucler → ajouter des éléments.

# version classique : 3 lignes
carres = []
for n in range(10):
    carres.append(n ** 2)

# version compréhension : 1 expression, même résultat
carres = [n ** 2 for n in range(10)]

la forme générale est à connaître avec le nom de chaque partie :

[ expression for élément in itérable if condition ]

  • expression : ce qu'on garde (ce qui sera placé dans la nouvelle collection) ;
  • for élément in itérable : ce qu'on parcourt ;
  • if condition : le filtre, optionnel.

les trois exemples du cours montrent les trois usages : filtrer, transformer, et choisir entre deux valeurs.

notes = [12, 15, 8, 17, 9]

admis    = [n for n in notes if n >= 10]                        # filtrer      -> [12, 15, 17]
bonus    = [min(n + 2, 20) for n in notes]                      # transformer  -> [14, 17, 10, 19, 11]
mentions = ["admis" if n >= 10 else "ajourné" for n in notes]   # choisir      -> une étiquette par note
piège qcm classique. il y a deux if différents. le if placé à la fin est un filtre : il retire des éléments (la liste obtenue peut être plus courte). le if … else placé au début, dans l'expression, est un choix : il garde tous les éléments et décide seulement de la valeur (même longueur que l'original). on ne peut pas mettre de else dans le filtre de fin.

compréhensions de dictionnaire et d'ensemble

le même principe s'applique aux dictionnaires (accolades avec clé: valeur) et aux ensembles (accolades avec une seule expression).

noms  = ["dupont", "martin", "bernard"]
notes = [13.5, 9.0, 16.25]

# dict : {clé: valeur for ...}
carnet = {nom: note for nom, note in zip(noms, notes)}
# {'dupont': 13.5, 'martin': 9.0, 'bernard': 16.25}

# inverser un dictionnaire (les valeurs deviennent les clés)
inverse = {v: k for k, v in carnet.items()}

# filtrer un dictionnaire
recus = {nom: n for nom, n in carnet.items() if n >= 10}
# {'dupont': 13.5, 'bernard': 16.25}

# set : pas de doublons
initiales = {nom[0] for nom in noms}       # {'d', 'm', 'b'}
pour comprendre. zip(noms, notes) associe les deux listes élément par élément et produit des paires : ("dupont", 13.5), ("martin", 9.0)… carnet.items() produit les paires (clé, valeur) du dictionnaire. dans les deux cas, for nom, note in … décompose chaque paire en deux variables. attention en inversant un dictionnaire : si deux clés ont la même valeur, une seule survit, puisque les clés sont uniques.

2.8 les fonctions de haut niveau

une fonction de haut niveau est une fonction qui prend une autre fonction en paramètre. en python, une fonction est une valeur comme une autre : on peut la passer à map, filter ou sorted pour leur dire quoi faire sur chaque élément.

lambda

définition du cours. une fonction anonyme, avec une seule expression. syntaxe : lambda paramètres: expression.

carre = lambda x: x ** 2
print(carre(5))              # 25

addition = lambda a, b: a + b   # plusieurs paramètres possibles
  • les fonctions lambda sont utilisées seulement pour une fonction simple ;
  • elles acceptent plusieurs paramètres ;
  • la valeur de l'expression est automatiquement renvoyée : il n'y a pas de return.

map

définition du cours. une fonction qui effectue la même opération sur les éléments d'une collection.

def myfunc(n):
    return len(n)

x = map(myfunc, ('apple', 'banana', 'cherry'))
print(list(x))               # [5, 6, 6]

# même chose avec une lambda
x = map(lambda n: len(n), ('apple', 'banana', 'cherry'))

filter

définition du cours. une fonction qui sélectionne les éléments d'une collection qui respectent une condition donnée. la fonction passée en paramètre renvoie true (on garde) ou false (on écarte).

ages = [5, 12, 17, 18, 24, 32]

def myfunc(x):
    if x < 18:
        return false
    else:
        return true

adults = filter(myfunc, ages)
print(list(adults))          # [18, 24, 32]

# même chose avec une lambda
adults = filter(lambda x: x >= 18, ages)
piège qcm. map et filter ne renvoient pas une liste mais un itérateur : les valeurs ne sont calculées que lorsqu'on les demande. print(map(...)) affiche quelque chose comme <map object at 0x…>. c'est pour cela que le cours écrit print(list(x)). ordre des arguments : la fonction d'abord, la collection ensuite.

sorted

définition du cours. une fonction qui ordonne les éléments selon un critère donné. le critère est fourni par le paramètre key : une fonction appliquée à chaque élément, dont le résultat sert à comparer.

def myfunc(n):
    return abs(10 - n)       # distance à 10

a = (5, 3, 1, 11, 2, 12, 17)
x = sorted(a, key=myfunc)
print(x)                     # [11, 12, 5, 3, 17, 2, 1]  (du plus proche de 10 au plus éloigné)

points à retenir sur sorted :

  • elle renvoie toujours une nouvelle liste, quel que soit l'itérable de départ (ici un tuple), et ne modifie pas l'original ;
  • reverse=true trie en ordre décroissant ;
  • pour un tri à plusieurs critères (tp2), la clé renvoie un tuple : les tuples sont comparés élément par élément. pour inverser un seul critère numérique, on met un signe moins.
employes = [
    {"nom": "sophie", "anciennete": 5, "salaire": 42000},
    {"nom": "marc",   "anciennete": 5, "salaire": 39000},
]
# salaire décroissant
sorted(employes, key=lambda e: e["salaire"], reverse=true)
# ancienneté croissante, puis salaire décroissant en cas d'égalité
sorted(employes, key=lambda e: (e["anciennete"], -e["salaire"]))
pour comprendre. ne confonds pas sorted(liste), qui renvoie une nouvelle liste, et liste.sort(), méthode des listes qui trie sur place et renvoie none. écrire x = liste.sort() donne x = none.

2.9 itérables, itérateurs et générateurs

les itérables

définition du cours. un itérable est un objet python dont on peut parcourir les éléments un par un, par exemple avec une boucle for. les itérables cités : les listes, dictionnaires, tuples, ensembles, les chaînes de caractères, et range().

les itérateurs

définition du cours. un itérateur est un objet qui permet de parcourir les éléments d'un itérable un par un. il mémorise où il en est dans le parcours et fournit l'élément suivant.

on obtient un itérateur avec la fonction iter(), et on lui demande l'élément suivant avec next() :

nombres = [10, 20, 30]
it = iter(nombres)       # on crée un itérateur sur la liste
print(next(it))          # 10
print(next(it))          # 20
print(next(it))          # 30
print(next(it))          # stopiteration : il n'y a plus rien à fournir

quand l'itérateur est épuisé, next() lève l'exception stopiteration. c'est exactement ce mécanisme que la boucle for utilise en coulisses. le cours met les deux écritures côte à côte : elles sont équivalentes.

# ce qu'on écrit
nombres = [10, 20, 30]
for nombre in nombres:
    print(nombre)

# ce que python fait réellement
nombres = [10, 20, 30]
it = iter(nombres)
while true:
    try:
        nombre = next(it)
        print(nombre)
    except stopiteration:
        break
pour comprendre la différence itérable / itérateur. l'itérable est la collection (le livre) ; l'itérateur est le marque-page qui sait à quelle page on en est. on peut créer plusieurs itérateurs indépendants sur la même liste. un itérateur ne se parcourt qu'une seule fois : une fois épuisé, il ne revient pas au début, il faut en recréer un avec iter().

les générateurs

définition du cours. un générateur est un type particulier d'itérateur qui produit ses valeurs une par une, au fur et à mesure qu'elles sont demandées, au lieu de les stocker toutes en mémoire.

on écrit un générateur comme une fonction, mais avec le mot-clé yield à la place de return :

def nombres():
    yield 1
    yield 2
    yield 3

g = nombres()            # appeler la fonction n'exécute rien : cela crée le générateur
print(next(g))           # 1
print(next(g))           # 2
print(next(g))           # 3

le principe de mémoire du générateur (encadré du tp2) : un générateur suspend son exécution à chaque yield en sauvegardant l'état local de ses variables, puis la reprend là où elle s'était arrêtée lors de la demande du terme suivant. return termine une fonction et oublie tout ; yield la met en pause.

la phrase clé de la slide : « tout générateur est un itérateur ». on peut donc le parcourir avec next() ou, plus simplement, avec une boucle for :

def nombres():
    for i in range(5):
        yield i

for nombre in nombres():
    print(nombre)        # 0, 1, 2, 3, 4

l'intérêt est la mémoire : une liste d'un million de valeurs occupe un million de cases ; un générateur qui produit un million de valeurs n'en garde qu'une à la fois. c'est ce qui permet de construire des « flux de données efficaces », y compris sur des suites très longues ou infinies.

pièges qcm. (1) tout générateur est un itérateur, mais l'inverse est faux : iter([1, 2]) est un itérateur sans être un générateur. (2) une liste est un itérable, pas un itérateur : next([1, 2]) est une erreur, il faut d'abord iter(). (3) comme tout itérateur, un générateur se consomme une seule fois. (4) une fonction qui contient yield ne s'exécute pas quand on l'appelle : elle renvoie un objet générateur.

2.10 l'écriture idiomatique

un idiome est la manière naturelle, reconnue par la communauté, d'exprimer une idée dans un langage. on parle de code « pythonique ». le tp2 résume l'objectif : transformer du code impératif et verbeux en code pythonique, performant et lisible. le cours liste huit idiomes, chacun présenté comme « à éviter → à préférer ».

idiomeà éviterà préférer
parcourir une collection
for i in range(len(names)):
    print(names[i])
for name in names:
    print(name)
utiliser les compréhensions
squares = []
for x in range(10):
    squares.append(x ** 2)
squares = [x ** 2 for x in range(10)]
utiliser enumerate() quand on a besoin de l'index et de l'élément
for i in range(len(names)):
    print(i, names[i])
for i, name in enumerate(names):
    print(i, name)
décomposer les structures (unpacking)
point = (10, 20)
x = point[0]
y = point[1]
point = (10, 20)
x, y = point
chercher un élément avec in
for name in names:
    if name == "alice":
        ...
if "alice" in names:
    ...
utiliser les valeurs de vérité (truthiness)
if len(names) > 0:
    print("la liste n'est pas vide")
if names:
    print("la liste n'est pas vide")
utiliser dict.get()
if "age" in person:
    age = person["age"]
else:
    age = 0
age = person.get("age", 0)
utiliser with pour gérer les ressources
file = open("data.txt")
content = file.read()
file.close()
with open("data.txt") as file:
    content = file.read()

quelques explications sur les idiomes les moins évidents :

  • valeurs de vérité. dans un if, toute collection vide vaut false et toute collection non vide vaut true. sont aussi considérés comme faux : 0, "" (chaîne vide), none, [], (), {}, set().
  • dict.get(clé, défaut) renvoie la valeur si la clé existe, et la valeur par défaut sinon, sans lever de keyerror. sans second argument, le défaut est none. get ne modifie pas le dictionnaire.
  • with garantit que la ressource (ici le fichier) est fermée automatiquement à la sortie du bloc, même si une erreur se produit au milieu. avec la version manuelle, une exception entre open et close laisse le fichier ouvert.
  • décomposition dans une boucle (tp2) : for nom, prenom, notes in etudiants: décompose directement chaque tuple de la liste.
  • fonctions intégrées (tp2) : calculer une moyenne avec sum(notes) / len(notes) plutôt qu'avec une boucle et un accumulateur.
à retenir du chapitre 2.
  • list : ordonnée, mutable · tuple : ordonné, immuable, hashable si ses éléments le sont · set : unique, non ordonné, mutable, éléments hashables · dict : paires clé–valeur, mutable, clés uniques et hashables, valeurs libres.
  • compréhension : [expression for élément in itérable if condition], filtre optionnel ; existe pour list, dict et set.
  • lambda : anonyme, une seule expression. map : même opération sur chaque élément. filter : sélectionne selon une condition. sorted : ordonne selon key, renvoie une nouvelle liste.
  • itérable : parcourable. itérateur : mémorise sa position, iter() / next() / stopiteration. générateur : itérateur écrit avec yield, valeurs produites à la demande.
  • huit idiomes : parcours direct, compréhensions, enumerate, décomposition, in, valeurs de vérité, dict.get, with.

chapitre 3 modularisation et organisation de projet

plan de la séquence : 1. imports · 2. modules · 3. packages · 4. architecture d'un projet

tant qu'un programme tient dans un fichier, tout va bien. dès qu'il grossit, il faut le découper en morceaux réutilisables et savoir les relier entre eux. ce chapitre répond à trois questions : comment python va-t-il chercher du code situé ailleurs (les imports) ? comment ce code est-il rangé (modules, packages) ? et comment organise-t-on le dossier d'un projet entier ?

3.1 les syntaxes d'importation

le cours distingue deux syntaxes.

l'import global importe le module entier. on accède ensuite à son contenu en le préfixant du nom du module :

import math
print(math.sqrt(16))     # on écrit math.sqrt

l'import ciblé importe uniquement un nom précis du module. on l'utilise ensuite directement, sans préfixe :

from math import sqrt
print(sqrt(16))          # on écrit sqrt tout court
pour comprendre. avec l'import global, on voit toujours d'où vient une fonction (math.sqrt), au prix d'un code un peu plus long. avec l'import ciblé, le code est plus court, mais le nom sqrt arrive directement dans ton fichier : si tu définis toi-même une fonction sqrt, elle entre en conflit avec lui. après from math import sqrt, le nom math n'existe pas dans ton fichier : math.pi échoue.

3.2 les alias

définition du cours. les alias sont des raccourcis ou des surnoms donnés aux bibliothèques, introduits par le mot-clé as. ils servent à quatre choses :

  • raccourcir le code : éviter de répéter les noms complets des bibliothèques à chaque utilisation ;
  • éviter les conflits de noms entre bibliothèques ;
  • faciliter le remplacement d'un outil : en utilisant le même alias pour le nouvel outil, on évite de modifier le reste du code ;
  • respecter les conventions de la communauté.
import numpy as np
import pandas as pd
import matplotlib.pyplot as plt

dataframe = pd.read_csv("data.csv")

les alias np, pd et plt sont des conventions universelles : tout développeur python les reconnaît. un alias fonctionne aussi sur un import ciblé (from math import sqrt as racine) et sur un module standard (import datetime as dt, demandé dans le tp3).

3.3 sys.path : où python cherche les modules

définition du cours. sys.path est une liste de chemins dans lesquels python va chercher les bibliothèques importées. elle se constitue de :

  • le dossier des bibliothèques standard ;
  • le dossier des bibliothèques tierces (le site-packages) ;
  • le dossier courant : le répertoire qui contient le script exécuté.

la règle de recherche : python parcourt la liste des chemins dans l'ordre, cherche le module importé et s'arrête dès qu'il le trouve.

import sys
print(sys.path)          # une simple liste python de chaînes : les dossiers de recherche
pour comprendre. deux conséquences pratiques. (1) si le module n'est dans aucun des dossiers de la liste, on obtient modulenotfounderror: no module named '…'. (2) comme python s'arrête au premier trouvé, un fichier de ton projet qui porte le même nom qu'un module connu le masque : en pratique le dossier du script exécuté est placé en tête de liste, donc un fichier random.py ou math.py à côté de ton script sera importé à la place du vrai module. ne nomme jamais un fichier comme une bibliothèque.

3.4 comment python charge un module

une fois le fichier trouvé, voici ce qui se passe, d'après le cours :

  1. pour chaque bibliothèque importée, python exécute le fichier .py en entier, même si l'import cible une seule fonction.
  2. le module chargé est stocké dans le dictionnaire sys.modules, pour éviter de le recharger une seconde fois.
  3. python crée une variable locale (le nom du module) dans ton script pour te donner accès à son contenu.
  4. en cas d'alias, l'alias est utilisé comme nom de variable.

le premier point est celui qui surprend : from outils import addition exécute tout outils.py, y compris les print et les appels de fonction qui traînent à la fin du fichier. le second explique pourquoi importer dix fois le même module dans dix fichiers ne coûte rien : le fichier n'est exécuté qu'à la première importation, les suivantes réutilisent l'objet rangé dans sys.modules.

# outils.py
print("chargement de outils")

def addition(a, b):
    return a + b
# programme.py
from outils import addition     # affiche "chargement de outils" : tout le fichier est exécuté
from outils import addition     # n'affiche rien : le module est déjà dans sys.modules
import outils as o              # la variable créée s'appelle o, pas outils

3.5 le module

définition du cours. un module est un fichier python (.py) qui contient du code — des fonctions, des classes ou des variables — réutilisable dans d'autres programmes.

un même fichier .py peut être exécuté de deux façons :

$ python hello.py        # comme fichier : on donne le chemin du fichier, avec l'extension
$ python -m hello        # comme module : on donne le nom du module, sans extension
pour comprendre la différence. avec python hello.py, python reçoit un chemin de fichier et l'exécute comme un script isolé. avec python -m hello, python reçoit un nom de module : il le cherche via sys.path, exactement comme le ferait un import, puis l'exécute. pour un module rangé dans un package on écrit le chemin avec des points : python -m convertisseur.main. cette seconde forme est celle qui permet aux imports relatifs de fonctionner (voir 3.9).

3.6 la variable __name__

définition du cours. __name__ est une variable spéciale intégrée (une dunder variable, pour double underscore) qui contient le nom du module en cours d'exécution. sa valeur dépend de la façon dont le fichier est exécuté :

situationvaleur de __name__
le fichier est exécuté directement"__main__"
le fichier est importéle nom du module (le fichier .py sans extension)

de là vient un bloc de code très courant en python :

if __name__ == "__main__":
    print("script lancé directement")

ce bloc permet d'insérer un code qui s'exécute seulement si le fichier est lancé directement. il prend tout son sens avec la règle 3.4 : puisqu'un import exécute le fichier en entier, tout ce qui n'est pas protégé par cette garde s'exécuterait aussi à l'import. on place donc le « programme principal » sous la garde, et les fonctions réutilisables au-dessus.

# convertisseur.py
def celsius_vers_fahrenheit(c):
    return (c * 9 / 5) + 32

if __name__ == "__main__":
    # exécuté avec "python convertisseur.py", ignoré avec "import convertisseur"
    print(celsius_vers_fahrenheit(25))
pièges qcm. (1) __name__ vaut la chaîne "__main__" : il faut les guillemets dans la comparaison. (2) importé, un fichier outils.py a __name__ == "outils", sans .py. (3) lancé avec python -m hello, le fichier est aussi le point d'entrée : __name__ vaut encore "__main__".

3.7 le package

définition du cours. un package est un dossier regroupant plusieurs modules python, généralement identifié par un fichier __init__.py, permettant d'organiser le code de manière hiérarchique. un package peut contenir des sous-packages.

convertisseur/               <- package
├── __init__.py
├── constantes.py            <- module
├── affichage.py             <- module
└── conversions/             <- sous-package
    ├── __init__.py
    ├── temperature.py
    └── longueur.py

dans un import, on descend dans la hiérarchie avec des points : import convertisseur.conversions.temperature, ou from convertisseur.conversions.temperature import celsius_vers_kelvin.

3.8 le fichier __init__.py

définition du cours. c'est un fichier qui sert de porte d'entrée du package. trois points :

  • il s'exécute lors de l'importation du package ;
  • il permet de simplifier les imports en exposant directement les fonctions, classes ou variables principales à la racine du package ;
  • dans les anciennes versions de python, son existence était indispensable pour désigner le dossier comme package ; maintenant le fichier est souvent vide.

« exposer à la racine » est le point le plus utile. sans rien dans __init__.py, l'utilisateur doit connaître toute l'arborescence interne :

from convertisseur.conversions.temperature import celsius_vers_kelvin

si le __init__.py du package importe lui-même cette fonction, elle devient disponible directement au niveau du package :

# convertisseur/__init__.py
from .conversions import celsius_vers_kelvin
from .affichage import entete, formater
__version__ = "0.1.0"
# ailleurs : l'utilisateur n'a plus besoin de connaître la structure interne
from convertisseur import celsius_vers_kelvin, entete
piège qcm. attention à la formulation : __init__.py identifie généralement un package, mais il n'est plus indispensable dans les versions récentes de python et il est souvent vide. dire « sans __init__.py, le dossier ne peut pas être importé » est faux aujourd'hui. importer un sous-package exécute d'abord le __init__.py du package parent, puis celui du sous-package.

3.9 chemins absolus et chemins relatifs

pour importer un module dans un autre, le développeur peut spécifier le chemin absolu (à partir du paquet racine) ou bien le chemin relatif au module importateur.

import absoluimport relatif
écriturefrom convertisseur.constantes import kelvin_offsetfrom ..constantes import miles_par_km
point de départle paquet racinel'emplacement du module qui importe
comment python résoutil cherche le module dans la liste des chemins définis par sys.pathil doit connaître l'arborescence du package pour trouver les modules importés

la notation des imports relatifs (rappel du tp3) : un point . désigne le package courant, deux points .. désignent le package parent.

# dans convertisseur/conversions/longueur.py
from .temperature import celsius_vers_kelvin    # .  = même package (conversions)
from ..constantes import miles_par_km           # .. = package parent (convertisseur)
pour comprendre. l'import absolu est explicite et se lit sans connaître l'emplacement du fichier ; mais il casse si on renomme le paquet racine. l'import relatif est court et survit à un renommage du paquet ; mais il ne fonctionne que si python sait à quel package appartient le fichier — c'est le rôle de __package__.

3.10 la variable __package__

définition du cours. c'est une variable spéciale qui indique à python à quel paquet appartient le module courant.

  • en cas d'importation avec chemins relatifs, python se base sur cette variable pour connaître la hiérarchie.
  • le __package__ d'un fichier python exécuté directement (python test.py) contient none.

la conséquence est directe : un fichier lancé directement n'appartient, du point de vue de python, à aucun package. s'il contient un import relatif, python ne sait pas par rapport à quoi le résoudre et s'arrête avec cette erreur (vérifiée sur le projet du tp3) :

$ python convertisseur/conversions/longueur.py
importerror: attempted relative import with no known parent package

c'est la raison pour laquelle le tp3 lance le programme comme module, depuis le dossier src/ :

$ cd src
$ python -m convertisseur.main

avec -m, python connaît le package d'appartenance (__package__ vaut "convertisseur") et le dossier courant src/ est dans sys.path : les imports absolus et relatifs fonctionnent. à l'inverse, python convertisseur/main.py échoue avec modulenotfounderror: no module named 'convertisseur', car le dossier ajouté à sys.path est alors src/convertisseur/, dans lequel il n'y a pas de dossier convertisseur.

3.11 et une bibliothèque, alors ?

définition du cours. « bibliothèque » est juste un terme générique qui désigne tout ensemble de code réutilisable (modules ou paquets) mis à disposition des développeurs. ce n'est pas une notion technique de python, contrairement à module et package.

termece que c'est concrètement
moduleun fichier .py
packageun dossier de modules (avec généralement un __init__.py), pouvant contenir des sous-packages
bibliothèqueterme générique : n'importe quel ensemble de code réutilisable, module ou package

(3) les fichiers de test portent le préfixe test_ et reprennent le nom du module testé (test_module_a.py pour module_a.py). (4) ce sont des conventions, pas des obligations du langage.

  • chargement : fichier exécuté en entier, stocké dans sys.modules, variable locale créée, l'alias sert de nom.
  • module = fichier .py ; package = dossier de modules ; bibliothèque = terme générique.
  • __name__ : "__main__" si lancé directement, nom du module si importé. __package__ : paquet d'appartenance, none si lancé directement.
  • __init__.py : exécuté à l'import du package, expose des noms à la racine, plus indispensable, souvent vide.
  • absolu : depuis le paquet racine, résolu via sys.path. relatif : . package courant, .. package parent, exige de connaître l'arborescence.
  • architecture : .venv, .env, .env.example, .gitignore, pyproject.toml, readme.md, src, tests.

chapitre 4 gestion des dépendances et environnements

plan de la séquence : 1. dépendances et résolution de versions · 2. environnements virtuels · 3. fichier de description de projet · 4. arguments en ligne de commande

4.1 les dépendances

définition du cours. une dépendance est une bibliothèque externe dont un projet (ou une autre bibliothèque) a besoin pour fonctionner. on en distingue deux sortes :

  • les dépendances directes : celles que le projet déclare lui-même (on les installe avec pip install) ;
  • les dépendances transitives : celles dont dépendent à leur tour les dépendances directes. l'exemple du cours : requests dépend de urllib3. si ton projet utilise requests, alors requests est une dépendance directe et urllib3 une dépendance transitive (on dit aussi indirecte).

tu ne demandes jamais explicitement une dépendance transitive : le gestionnaire de paquets l'installe automatiquement, parce que ta dépendance directe en a besoin. un projet avec trois dépendances directes peut ainsi se retrouver avec vingt bibliothèques installées.

4.2 les versions

définition du cours. une version est un numéro qui identifie un état précis d'une bibliothèque à un moment donné. chaque fois que les auteurs publient des changements (correction, amélioration, nouveauté), ils publient une nouvelle version. le format général est :

majeur . mineur . correctif    (par exemple 2.34.1)

numérosignificationexemple
majeurchangements incompatibles : du code qui marchait peut casser.2.34.1 → 3.0.0
mineurnouvelles fonctionnalités, sans rien casser.2.34.1 → 2.35.0
correctifcorrections de bugs, sans rien casser.2.34.1 → 2.34.2
pour comprendre. cette convention permet de juger le risque d'une mise à jour d'un seul coup d'œil : passer de 2.34.1 à 2.34.2 ou à 2.35.0 est en principe sans danger, passer à 3.0.0 demande de relire son code. la « résolution de versions » du titre de la séquence désigne le travail du gestionnaire de paquets : trouver un jeu de versions qui satisfait en même temps les exigences de toutes les dépendances, directes et transitives.

4.3 où s'installent les bibliothèques, et le problème que cela pose

un module (ou package) installé avec pip install, ou qui existe par défaut (bibliothèque standard), est automatiquement placé dans le dossier de python :

  • lib pour les bibliothèques standard ;
  • lib/site-packages pour les bibliothèques tierces.

ce sont précisément les deux premiers dossiers de sys.path vus au chapitre 3. tous les projets de la machine partagent donc le même site-packages, et un dossier ne peut contenir qu'une seule version d'une bibliothèque donnée. d'où la problématique posée par le cours :

comment gérer deux projets qui dépendent de la même bibliothèque, mais avec deux versions différentes ?

si le projet a a besoin de numpy 1.x et le projet b de numpy 2.x, installer l'une écrase l'autre : l'un des deux projets cesse de fonctionner.

4.4 l'environnement virtuel

définition du cours. un environnement virtuel est un dossier (souvent .venv/) contenant :

  • une copie ou un lien vers l'interpréteur python ;
  • son propre dossier site-packages, où s'installent les bibliothèques du projet.

c'est la réponse à la problématique : chaque projet reçoit son propre site-packages, donc ses propres versions. les projets ne se marchent plus dessus, et le python global reste propre.

l'activation. activer l'environnement modifie le path du terminal pour que python et pip désignent ceux de l'environnement.

pour comprendre. le path est la liste de dossiers dans laquelle le terminal cherche un programme quand tu tapes son nom. l'activation place le dossier de l'environnement en tête de cette liste : la commande python lance alors l'interpréteur de .venv, et pip install installe dans le site-packages de .venv. rien d'autre ne change : l'activation ne vaut que pour le terminal courant. commandes manuelles : python -m venv .venv pour créer, source .venv/bin/activate (linux, macos) ou .venv\scripts\activate (windows) pour activer, deactivate pour quitter.

4.5 uv, le gestionnaire de paquets moderne

définition du cours. uv est un gestionnaire de paquets moderne. il permet de :

  • gérer les paquets (installation, mise à jour, désinstallation) ;
  • gérer les environnements virtuels ;
  • assurer la reproductibilité des projets.

pourquoi uv ? il est souvent 10 à 100 fois plus rapide que pip, compatible avec pip, et compatible avec les fichiers du standard actuel (le pyproject.toml). là où il fallait plusieurs outils (pip pour les paquets, venv pour les environnements), uv fait tout.

installation (tp4) : un script selon le système, ou via pip ; on vérifie avec uv --version.

4.6 la reproductibilité

définition du cours. un projet reproductible est un projet qui permet d'obtenir exactement le même fonctionnement et les mêmes résultats, sur n'importe quelle machine et à n'importe quel moment.

pour cela, une description détaillée des dépendances du projet doit être fournie, afin de garantir que le programme s'exécutera dans le même environnement d'exécution que l'original. c'est le « ça marche sur ma machine » qu'on cherche à éliminer : sans description précise, ton camarade installe la dernière version d'une bibliothèque, différente de la tienne, et le programme se comporte autrement. deux fichiers portent cette description.

4.7 le fichier pyproject.toml

définition du cours. c'est le fichier de configuration d'un projet python : il décrit le projet (nom, version, version de python requise) et liste les dépendances dont il a besoin pour fonctionner.

[project]
name = "convertisseur"
version = "0.1.0"
requires-python = ">=3.13"
dependencies = [
    "numpy>=2.0",
]

lecture ligne par ligne : name et version identifient le projet ; requires-python indique la version minimale de python ; dependencies est la liste des dépendances directes, chacune avec une contrainte de version. "numpy>=2.0" signifie « numpy en version 2.0 ou supérieure » : ce n'est pas une version exacte, plusieurs versions peuvent convenir. on n'édite pas ce fichier à la main pour ajouter une dépendance : uv add s'en charge.

4.8 le fichier uv.lock

définition du cours. c'est le fichier de verrouillage généré par uv. il enregistre la liste exacte de toutes les dépendances du projet (directes et indirectes), avec leur version précise, leur provenance et leurs empreintes (hashes) de vérification.

4.9 ce qu'on fournit pour reproduire un environnement

pour un projet reproductible, on doit fournir :

  • le code source ;
  • pyproject.toml ;
  • uv.lock ;
  • readme.md ;
  • .venv — barré sur la slide : on ne fournit pas le dossier .venv.

pourquoi ne pas livrer .venv ? parce qu'il est lourd, qu'il est lié à la machine et au système qui l'ont créé (il contient un lien vers ton interpréteur python), et surtout qu'il est inutile : avec pyproject.toml et uv.lock, n'importe qui le reconstruit à l'identique avec uv sync. c'est aussi pour cela que .venv figure dans le .gitignore, et que le livrable du tp4 demande les sources, pyproject.toml, uv.lock et le readme.md, pas l'environnement.

lien avec le chapitre 1. requirements.txt (pip) et pyproject.toml + uv.lock (uv) poursuivent le même but : la reproductibilité. le requirements.txt issu de pip freeze est une simple liste nom==version qui mélange dépendances directes et transitives ; le couple de uv sépare ce que tu demandes (pyproject.toml) de ce qui est verrouillé (uv.lock), et ajoute provenance et hashes.

4.10 les arguments en ligne de commande : la motivation

le cours repart du convertisseur du tp3 :

def celsius_vers_fahrenheit(c):
    return (c * 9 / 5) + 32

if __name__ == "__main__":
    c = 25
    print(celsius_vers_fahrenheit(c))

la valeur 25 est écrite « en dur » dans le code. et si on veut utiliser le même outil pour une autre valeur ? il faudrait modifier le fichier à chaque fois. les arguments en ligne de commande permettent d'utiliser le même outil pour différents paramètres, fournis au lancement :

$ python hello.py --valeur 30
$ python hello.py --valeur -10

pourquoi pas input() ?

input() permet de suspendre l'exécution d'un programme et de recevoir une entrée de la part de l'utilisateur :

if __name__ == "__main__":
    c = float(input("veuillez entrer une valeur:"))
    print(celsius_vers_fahrenheit(c))

le problème, d'après le cours : l'exécution est suspendue en attendant une valeur de la part de l'utilisateur. le programme a besoin d'un humain devant le clavier : on ne peut pas l'enchaîner dans un script, le lancer automatiquement la nuit ou l'appeler depuis un autre outil. avec des arguments, tout est fourni dès le lancement et le programme tourne sans interruption — c'est ce qu'attend un environnement devops.

4.11 argparse

argparse est le module standard (rien à installer) pour construire un outil en ligne de commande (cli). l'utilisation tient en trois étapes.

import argparse

# 1. création du parser
parser = argparse.argumentparser(
    description="convertit une température entre celsius et fahrenheit.")

# 2. ajout d'un argument
parser.add_argument("valeur", type=float, help="température à convertir")

# 3. récupération des arguments
args = parser.parse_args()

print(args.valeur)       # chaque argument devient un attribut de args

parse_args() lit ce que l'utilisateur a tapé après le nom du script, le vérifie, le convertit, et renvoie un objet dont chaque argument est un attribut (args.valeur).

les paramètres d'un argument

paramètredéfinition du cours
nomsans tiret, l'argument est positionnel : obligatoire, identifié par sa place. avec --, c'est une option : identifiée par son nom, généralement facultative.
nom courtalias abrégé d'une option, avec un seul tiret. on peut donner les deux : "-v", "--verbose".
typefonction de conversion appliquée à la chaîne reçue. sans type, tout reste une chaîne (str).
defaultvaleur utilisée si l'option n'est pas fournie.
choicesliste des valeurs autorisées. toute autre valeur provoque une erreur.
helptexte affiché dans --help pour décrire l'argument.

un exemple complet qui utilise tous ces paramètres, avec ses sorties réelles :

import argparse

def celsius_vers_fahrenheit(c):
    return (c * 9 / 5) + 32

def fahrenheit_vers_celsius(f):
    return (f - 32) * 5 / 9

if __name__ == "__main__":
    parser = argparse.argumentparser(
        description="convertit une température entre celsius et fahrenheit.")
    parser.add_argument("valeur", type=float, help="température à convertir")
    parser.add_argument("-u", "--unite", choices=["c", "f"], default="c",
                        help="unité de la valeur fournie (défaut : c)")
    parser.add_argument("-v", "--verbose", action="store_true",
                        help="afficher le détail")
    args = parser.parse_args()

    if args.unite == "c":
        resultat = celsius_vers_fahrenheit(args.valeur)
    else:
        resultat = fahrenheit_vers_celsius(args.valeur)

    if args.verbose:
        print("valeur :", args.valeur, "| unité :", args.unite)
    print(resultat)

$ python conv.py 77 --unite f -v

25.0
$ python conv.py
usage: conv.py [-h] [-u {c,f}] [-v] valeur
conv.py: error: the following arguments are required: valeur
$ python conv.py 25 -u k

$ python conv.py abc

on voit sur ces sorties ce qu'argparse fait gratuitement : il refuse un positionnel manquant, une valeur hors de choices, une valeur que type ne sait pas convertir, et il génère tout seul l'aide -h / --help à partir des textes description et help.

les options sans valeur : action (tp4)

certaines options sont de simples interrupteurs : elles ne sont pas suivies d'une valeur. on les déclare avec le paramètre action.

actionvaleur si l'option est absentevaleur si l'option est présente
"store_true"falsetrue
"store_false"truefalse

le paramètre dest choisit le nom de l'attribut dans args. le tp4 combine les deux :

parser.add_argument("--no-digits", action="store_false", dest="avec_chiffres")
# sans l'option : args.avec_chiffres vaut true  ; avec --no-digits : false
pièges qcm. (1) sans type, la valeur reçue est toujours une chaîne : "30" + 1 plante. (2) un positionnel est identifié par sa place, une option par son nom : l'ordre des options est libre. (3) nom court : un tiret (-v) ; nom long : deux (--verbose). (4) sans dest, le nom de l'attribut vient du nom long, les tirets devenant des underscores : --no-digits → args.no_digits. (5) une option non fournie et sans default vaut none.
à retenir du chapitre 4.
  • dépendance directe : déclarée par le projet. transitive : exigée par une dépendance directe (requests → urllib3).
  • version majeur.mineur.correctif : incompatible / nouveautés sans casser / corrections sans casser.
  • bibliothèques standard dans lib, tierces dans lib/site-packages ; problème : deux projets, deux versions de la même bibliothèque.
  • environnement virtuel : dossier .venv avec copie/lien de l'interpréteur et son propre site-packages ; l'activation modifie le path.
  • uv : paquets + environnements + reproductibilité ; 10 à 100 fois plus rapide que pip ; init, add, remove, venv, run, pip, sync, lock, tree.
  • pyproject.toml : décrit le projet et liste les dépendances. uv.lock : toutes les dépendances, versions précises, provenance, hashes.
  • à fournir : code source, pyproject.toml, uv.lock, readme.md — pas .venv.
  • input() suspend l'exécution ; argparse : parser → add_argument → parse_args ; paramètres nom, nom court, type, default, choices, help.

import random
import string


def generer_mot_de_passe(longueur: int = 12, avec_chiffres: bool = true,
                         avec_symboles: bool = true) -> str:
    alphabet = string.ascii_letters              # lettres minuscules et majuscules
    if avec_chiffres:
        alphabet += string.digits                # "0123456789"
    if avec_symboles:
        alphabet += string.punctuation           # symboles
    return "".join(random.choice(alphabet) for _ in range(longueur))

la traduction vers le langage machine, la vérification de certaines erreurs (syntaxe, typage…), et des optimisations adaptées à la machine cible. §1.2

code source → compilateur (cpython) → code intermédiaire (bytecode) → interpréteur (pvm) → exécution. §1.5

🏛️ programmation orientée objet — les 4 principes

📖 leçon — comprendre la poo depuis le début

la programmation orientée objet (poo) est un paradigme de programmation — une façon d'organiser et de penser le code. l'idée fondamentale : modéliser le monde réel sous forme d'objets. un objet est une entité qui regroupe des données (ce qu'il est, ses attributs) et des comportements (ce qu'il fait, ses méthodes).

une classe est le plan de construction de l'objet — le moule. un objet (ou instance) est ce qu'on fabrique avec ce moule. voiture est une classe ; votre peugeot 208 rouge immatriculée en 2023 est une instance de cette classe.

principe 1 — encapsulation

l'encapsulation consiste à regrouper les données et les méthodes qui les manipulent au sein d'un même objet, et à contrôler l'accès à ces données depuis l'extérieur. c'est le principe de la "boîte noire" : on expose une interface publique simple, et on cache la complexité interne.

concrètement : un objet comptebancaire expose les méthodes deposer() et retirer(), mais le solde interne n'est pas modifiable directement depuis l'extérieur. toute modification passe par les méthodes contrôlées. l'encapsulation protège l'intégrité des données.

en python, l'encapsulation s'exprime par convention : _attribut (un underscore) signale un attribut "protégé" — accessible mais non recommandé depuis l'extérieur. __attribut (deux underscores) déclenche le name mangling : python renomme l'attribut en _nomclasse__attribut pour le rendre plus difficile d'accès. les @property permettent de contrôler finement la lecture et l'écriture d'un attribut tout en gardant une syntaxe naturelle.

principe 2 — abstraction

l'abstraction consiste à exposer uniquement ce qui est nécessaire à l'utilisateur d'un objet, en cachant les détails d'implémentation. on modélise "ce que fait" un objet, pas "comment il le fait".

quand vous conduisez une voiture, vous interagissez avec le volant, l'accélérateur et le frein — vous n'avez pas besoin de comprendre comment fonctionne le moteur. c'est de l'abstraction. en programmation, les classes abstraites (abc — abstract base classes) formalisent ce principe : elles définissent une interface (quelles méthodes doivent exister) sans en donner l'implémentation. toute classe concrète qui hérite d'une abc doit implémenter toutes les méthodes abstraites, sinon python lève une typeerror à l'instanciation.

principe 3 — héritage

l'héritage permet à une classe fille (ou dérivée) de réutiliser et d'étendre le comportement d'une classe mère (ou parent). c'est une relation de type "est-un" : un chien est un animal, une questionqcm est une question.

l'héritage évite la duplication de code : les attributs et méthodes de la classe mère sont automatiquement disponibles dans la classe fille. la classe fille peut surcharger (override) les méthodes de la mère pour les spécialiser — tout en pouvant appeler la méthode originale via super(). c'est ainsi que auditeurlibre hérite de etudiant et en reprend tous les comportements sans réécrire une seule ligne.

principe 4 — polymorphisme

le polymorphisme (du grec "plusieurs formes") est la capacité pour des objets de types différents à répondre à la même interface. concrètement : on appelle la même méthode sur des objets différents, et chacun réagit selon sa propre implémentation.

dans le tp7, appeler question.evaluer(reponse) fonctionne que question soit une questionqcm, une questionnumerique ou une questionouverte — chacune évalue différemment, mais l'interface est identique. c'est du polymorphisme.

python va encore plus loin avec le duck typing : peu importe le type réel d'un objet, si un objet possède les attributs et méthodes attendus, il peut être utilisé. "si ça marche comme un canard et que ça fait coin-coin, c'est un canard." pas besoin d'héritage commun : si deux classes ont toutes les deux une méthode voler(), elles sont polymorphes vis-à-vis de cette méthode, qu'elles aient un ancêtre commun ou non.

🌐 http, sérialisation & sécurité

📖 leçon — comment les applications communiquent et échangent des données

le modèle client-serveur

sur le web, toute communication repose sur le modèle client-serveur. le client (votre script python, un navigateur, une appli mobile) envoie une requête à un serveur (une machine quelque part sur internet qui expose une api). le serveur traite la requête et renvoie une réponse.

le protocole http (hypertext transfer protocol) définit le format de ces échanges. il est stateless — chaque requête est indépendante, le serveur ne se souvient pas des requêtes précédentes. c'est pour ça qu'existent les tokens d'authentification : ils permettent d'identifier le client à chaque requête.

rest — une convention, pas un protocole

rest (representational state transfer) est un style architectural pour concevoir des apis web. une api rest organise ses ressources comme des noms (ex. /users, /products/42) et utilise les verbes http pour indiquer l'action : get pour lire, post pour créer, put/patch pour modifier, delete pour supprimer.

sérialisation — transformer des objets en données transportables

la sérialisation est l'opération qui consiste à convertir un objet python (un dictionnaire, une liste, une instance de classe) en un format transmissible sur le réseau ou stockable dans un fichier. la désérialisation est l'opération inverse.

json est le format dominant pour les apis web. il représente des structures hiérarchiques (objets, tableaux, chaînes, nombres, booléens, null) de façon universelle. presque tous les langages savent le lire et l'écrire — c'est la langue commune d'internet.

csv est adapté aux données tabulaires simples (comme une feuille excel). pas de hiérarchie, pas de types — tout est une chaîne de caractères. simple mais limité.

yaml est conçu pour être lu par des humains — sa syntaxe est minimaliste et intuitive. très utilisé pour les fichiers de configuration. sa faiblesse : yaml.load() peut exécuter du code arbitraire lors de la désérialisation, ce qui en fait un vecteur d'attaque. yaml.safe_load() est l'alternative sécurisée — elle ne fait que lire les données, sans exécuter quoi que ce soit.

sécurité des clés api — pourquoi le .env

une clé api est un identifiant secret qui vous authentifie auprès d'un service. si quelqu'un vole votre clé, il peut utiliser le service à votre place — et vous en faites payer la facture (ou pire, si c'est une api sensible). la règle absolue : une clé api ne doit jamais apparaître dans le code source. les dépôts git sont souvent publics, les archives partagées, les fichiers lus par des tiers.

la solution standard : stocker les clés dans un fichier .env exclu du dépôt git via .gitignore, et les lire dans le code via os.getenv(). le fichier .env.example (sans vraies valeurs) est commité pour guider les autres développeurs.

🤖 expressions régulières & logging

📖 leçon — pattern matching et journalisation en production

expressions régulières — un mini-langage pour les patterns

une expression régulière (regex) est une séquence de caractères qui décrit un pattern dans du texte. derrière chaque regex, il y a un automate fini — une machine à états qui parcourt le texte et vérifie si le pattern correspond. c'est un outil issu de la théorie des langages formels (années 1950), intégré dans presque tous les langages de programmation.

les regex permettent de : vérifier si une chaîne respecte un format (validation d'email, numéro de téléphone), extraire des sous-chaînes correspondant à un pattern, remplacer des occurrences dans un texte, découper une chaîne sur un pattern complexe.

la syntaxe est concise mais dense. quelques points clés à comprendre : un point . matche n'importe quel caractère (attention aux faux positifs), les groupes de capture () permettent d'extraire des sous-parties du match, et les quantificateurs (*, +, ?, {n,m}) contrôlent la répétition. les classes de caractères prédéfinies (\d, \w, \s) sont des raccourcis pour les patterns courants.

toujours utiliser les raw strings (r"pattern") pour les regex en python : sans le préfixe r, le backslash est interprété par python avant d'arriver au moteur regex, ce qui crée des bugs subtils.

re.search vs re.match vs re.findall

re.match() ne cherche qu'au début de la chaîne. re.search() cherche la première occurrence n'importe où dans la chaîne. re.findall() retourne toutes les occurrences sous forme de liste. re.sub() remplace toutes les occurrences. ces quatre fonctions couvrent 95% des besoins.

logging vs print() — la différence de professionnel

print() est parfait pendant le développement. en production, il pose plusieurs problèmes : pas de niveaux de sévérité (tout est identique), impossible de désactiver sélectivement, pas de timestamp, pas de contexte (quel fichier, quelle fonction), va toujours sur stdout.

le module logging résout tout cela. les niveaux (debug, info, warning, error, critical) permettent de filtrer : en développement, on affiche tout depuis debug ; en production, on affiche seulement warning et plus. les handlers définissent où vont les logs (console, fichier, service distant). les formatters définissent leur format (timestamp, niveau, nom du module…).

la bonne pratique est logger = logging.getlogger(__name__) dans chaque module. __name__ donne automatiquement le nom du module, ce qui permet de filtrer les logs par module dans une grosse application.

pathlib.path — la gestion de chemins orientée objet

l'ancien module os.path manipule les chemins comme des chaînes de caractères : os.path.join(dossier, "fichier.py"). c'est verbeux et pas naturel. pathlib.path (python 3.4+) traite les chemins comme des objets avec des méthodes : path(dossier) / "fichier.py". l'opérateur / surchargé est immédiatement lisible.

avantage crucial : pathlib gère automatiquement les différences entre windows (\) et unix (/). un code avec pathlib est portable sans modification. chaque méthode (`.exists()`, `.is_file()`, `.read_text()`, `.glob()`) est autodocumentée par son nom.

class question(abc):
    def __init__(self, enonce: str, points: float):
        self.enonce = enonce
        self.points = points

    @abstractmethod
    def evaluer(self, reponse) -> float:
        """retourne les points obtenus (0 ou self.points)"""
        ...

    def __str__(self) -> str:
        return f"[{self.__class__.__name__}] {self.enonce} ({self.points} pts)"

class questionqcm(question):
    def __init__(self, enonce: str, points: float,
                 options: list[str], bonne_reponse: int):
        super().__init__(enonce, points)
        self.options = options
        self.bonne_reponse = bonne_reponse  # index 0-based

    def evaluer(self, reponse: int) -> float:
        return self.points if reponse == self.bonne_reponse else 0.0

class questionvraifaux(question):
    def __init__(self, enonce: str, points: float, bonne_reponse: bool):
        super().__init__(enonce, points)
        self.bonne_reponse = bonne_reponse

    def evaluer(self, reponse: bool) -> float:
        return self.points if reponse == self.bonne_reponse else 0.0

class questionnumerique(question):
    def __init__(self, enonce: str, points: float,
                 bonne_reponse: float, tolerance: float = 0.01):
        super().__init__(enonce, points)
        self.bonne_reponse = bonne_reponse
        self.tolerance = tolerance

    def evaluer(self, reponse: float) -> float:
        return self.points if abs(reponse - self.bonne_reponse) <= self.tolerance else 0.0

class questionouverte(question):
    def __init__(self, enonce: str, points: float,
                 mots_cles: list[str]):
        super().__init__(enonce, points)
        self.mots_cles = [m.lower() for m in mots_cles]

    def evaluer(self, reponse: str) -> float:
        reponse_lower = reponse.lower()
        trouves = sum(1 for mc in self.mots_cles if mc in reponse_lower)
        ratio = trouves / len(self.mots_cles) if self.mots_cles else 0
        return round(self.points * ratio, 2)

def verifier_rendu(dossier_rendu: path) -> dict:
    """vérifie qu'un rendu étudiant contient les fichiers requis"""
    resultats = {}
    for etudiant in dossier_rendu.iterdir():
        if not etudiant.is_dir():
            continue
        fichiers = {f.name for f in etudiant.iterdir() if f.is_file()}
        manquants = fichiers_requis - fichiers
        resultats[etudiant.name] = {
            "complet": not manquants,
            "manquants": manquants
        }
        if manquants:
            logger.warning(f"{etudiant.name}: fichiers manquants: {manquants}")
        else:
            logger.info(f"{etudiant.name}: rendu complet ✓")
    return resultats

import re

def anonymiser_texte(texte: str) -> str:
    # remplacer emails
    texte = re.sub(r"[a-za-z0-9._%+-]+@[a-za-z0-9.-]+\.[a-za-z]{2,}",
